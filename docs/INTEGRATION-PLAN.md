# Tushonka Cleaner 1단계 통합 계획

목표는 기존 RAM 클리너와 서버 최적화 기능을 1.0.0 클라이언트 DLL 하나와 서버 DLL 하나로 옮기는 것입니다. 사용자 지시서가 설계·실행 범위이며 추가 승인, 커밋·푸시, 게임 설치·실행을 하지 않습니다. 하위 에이전트도 사용하지 않습니다.

- 클라이언트: 기존 메모리 플러그인을 진입점으로 사용하고, 서버 설정 화면·C1·C2는 일반 구성 요소로 직접 호출합니다. 설정 표시 속성도 하나로 합칩니다.
- 서버: 기존 최적화·진단·웹 경로와 RAM 웹 프록시를 같은 DLL에 보존하고 메타데이터는 하나로 합칩니다.
- 공통: 공유 설정 모델, 이전 설정 파서, 중복 설치 판정을 `src/Shared`에 두고 각 DLL에 소스로 포함합니다.
- 그래픽: `Graphics/ISceneCleanup.cs`와 무동작 구현만 만들고 `src/SceneCleanup`에는 접근하지 않습니다.
- 보호: 구형 RAM·서버 최적화·그래픽 모드 감지 시 겹치는 기능만 초기화하지 않고 로그와 화면에 경고합니다.
- 이전: 새 cfg가 없을 때만 구형 RAM cfg를 읽고 실제로 바인딩되는 동일한 절·키에만 적용합니다. 원본 cfg는 변경하지 않습니다.
- 배포: 게임 자동 복사 작업을 제거하고 Release 빌드에서 저장소의 `release/Tushonka-Cleaner-1.0.0.zip`만 만듭니다. 두 DLL·서버 config.json·GPL 전문·MIT 전문을 포함합니다.
- 검증: 원본 테스트 41개를 이전하고 설정 이전·중복 감지 사례를 추가합니다. 빌드·테스트·ZIP 검사 결과와 권한으로 막힌 검증을 구분합니다.

검토 초점은 초기 로딩 순서, 중복 설치 때 미초기화 객체 접근, 설정 이전 후 기본값 덮어쓰기, 같은 cfg에 합쳐진 서버 설정의 웹 노출 범위, 서버 웹 리소스 이름입니다.

## 실행 상태

소스 통합과 자체 검토를 마쳤습니다. 구형 RAM 감지 시 측정 스레드·수동 정리·웹 서버를 시작하지 않고, 서버 최적화는 일반 구성 요소로 계속 사용할 수 있도록 했습니다. 서버 웹의 두 기존 화면은 같은 모드 페이지에서 서로 이동할 수 있습니다. 원본 테스트 41개는 본문을 유지했고 추가 정책 테스트는 10개입니다.

정식 Release 빌드는 NuGet 사용자 설정 파일 읽기 거부로 복원 단계에서 중단됐습니다(경고 0·오류 3). 테스트도 복원 자산 파일이 없어 실행되지 않았습니다. 별도 읽기 전용 구문·형식 검사는 클라이언트·서버의 Release·BENCH 모두 오류 0·경고 0이며 DLL 생성·테스트 실행 결과는 아닙니다. ZIP과 인게임 동작은 미검증입니다. 하위 에이전트는 사용하지 않고 원본 대조와 자체 검토를 수행했습니다.

원본 `_import` 폴더 정리는 자동 승인 검토의 재귀 삭제 거부(`blocked by policy`)로 미완료입니다. 절대 경로로 지정한 동일 대상의 삭제도 거부되어 원본 폴더를 보존했습니다. 임시 이전 스크립트 두 개는 제거했습니다.
